# OLTP и OLAP: операционные и аналитические системы

> **Теги**: #db #oltp #olap #data #ddia

> *«Операционная система обычно ищет небольшое число записей по ключу (это называется точечный запрос). Записи вставляются, обновляются или удаляются по вводу пользователя. Поскольку эти приложения интерактивны, этот паттерн доступа стал известен как онлайн-обработка транзакций (OLTP)».*
> — Клеппман, Риккомини, «Высоконагруженные приложения», 2-е изд., гл. 1

## Краткое содержание
**OLTP** и **OLAP** — два принципиально разных **способа работы с базой данных**.
- **OLTP** — «рабочая» база приложения: много маленьких быстрых запросов от пользователей, которые читают и меняют отдельные записи.
- **OLAP** — аналитика: мало, но тяжёлых запросов, которые сканируют огромное число записей и считают итоги (суммы, средние, количества).

Из-за этой разницы их обычно держат в **разных системах** и связывают через **ETL**.

## 🧩 OLTP — Online Transaction Processing

**Расшифровка:** онлайн-обработка транзакций.
- **Online** — пользователь ждёт ответа прямо сейчас, запрос должен выполниться быстро.
- **Transaction** — исторически это коммерческая сделка (продажа, заказ, зарплата). Потом так стали называть **группу чтений и записей, образующих логическую единицу**. В гл. 1 книга использует слово нестрого: «чтения и записи с низкой задержкой».

**Как выглядит нагрузка:**
- **точечные запросы** — найти несколько записей **по ключу**;
- **вставка, обновление, удаление** отдельных записей по действиям пользователя;
- запросов **очень много**, каждый маленький;
- набор запросов **фиксированный, зашит в код** приложения;
- данные — **текущее состояние** (что есть сейчас).

**Пример — интернет-магазин:**
| Действие пользователя | Что делает БД |
|---|---|
| Открыть карточку товара | Прочитать одну запись по `id` |
| Положить в корзину | Вставить запись |
| Оформить заказ | Создать заказ, уменьшить остаток на складе |
| Изменить адрес доставки | Обновить одну запись |

**Почему пользователям не дают писать свой SQL в OLTP** (по книге):
- можно прочитать или изменить чужие данные, к которым нет доступа;
- тяжёлый запрос просадит производительность для всех остальных.

**Примеры СУБД (из табл. 1-2 книги):** MySQL, PostgreSQL, MongoDB; облачные — AWS Aurora, Azure SQL DB Hyperscale, Google Cloud Spanner.

## 📊 OLAP — Online Analytical Processing

**Расшифровка:** онлайн-аналитическая обработка.
- Что значит **online** здесь — по словам авторов, **неясно**. Вероятно, что аналитики работают с системой **интерактивно** и задают исследовательские запросы, а не только получают заранее заданные отчёты.

**Как выглядит нагрузка:**
- запрос **сканирует огромное число записей** и считает **агрегаты** (count, sum, average), а не возвращает отдельные записи;
- запросов **мало**, но каждый **сложный**;
- запросы **произвольные (ad-hoc)** — аналитик пишет SQL сам или через Tableau, Looker, Power BI;
- данные загружаются **массово (ETL)** или **потоком событий**;
- данные — **история событий** во времени.

**Пример — сеть супермаркетов (вопросы из книги):**
- Какая общая выручка у каждого магазина в январе?
- Насколько больше обычного бананов продали во время акции?
- Какую марку детского питания чаще покупают вместе с подгузниками марки X?

**Примеры СУБД (из табл. 1-2 книги):** Teradata, ClickHouse, Spark; облачные — Snowflake, Google BigQuery, Azure Synapse Analytics.

## ⚖️ Сравнение (табл. 1-1 из книги)

| Свойство | OLTP (операционные) | OLAP (аналитические) |
|---|---|---|
| Основной паттерн чтения | Точечные запросы по ключу | Агрегация по большому числу записей |
| Основной паттерн записи | Создание, обновление, удаление отдельных записей | Массовый импорт (ETL) или поток событий |
| Пользователь-человек | Конечный пользователь веб/мобильного приложения | Внутренний аналитик, поддержка решений |
| Машинное использование | Проверка, разрешено ли действие | Поиск паттернов мошенничества |
| Тип запросов | Фиксированные, заданы приложением | Произвольные, ad-hoc |
| Объём запросов | Много маленьких | Мало, каждый сложный |
| Что представляют данные | Текущее состояние | История событий |
| Размер данных | ГБ – ТБ | ТБ – ПБ |

> 💬 *Граница между OLTP и аналитикой не всегда чёткая*, — авторы подчёркивают, что это типичные черты, а не жёсткие правила.

## 🏗️ Почему их разделяют: хранилище данных и ETL

Почему аналитикам **не стоит ходить напрямую в OLTP** (по книге):
1. данные разбросаны по многим системам → трудно соединить в одном запросе (**data silos**);
2. схемы, удобные для OLTP, плохо подходят для аналитики;
3. аналитические запросы дорогие и бьют по производительности OLTP;
4. OLTP может быть в закрытой сети по требованиям безопасности.

**Решение — хранилище данных (data warehouse):** отдельная БД с **read-only копией** данных всех OLTP-систем. Данные туда доставляет **ETL**:

```
OLTP-базы ──Extract──► Transform (схема для анализа, чистка) ──Load──► Хранилище (OLAP)
```

- **ELT** — сначала загрузить, потом трансформировать внутри хранилища.
- **Озеро данных (data lake)** — «сырые» файлы любого формата для data scientists.
- **Reverse ETL** — результаты аналитики (например, обученная ML-модель) возвращаются обратно в операционные системы.

## 🔀 Промежуточные варианты

- **HTAP (hybrid transactional/analytical processing)** — OLTP и аналитика в одной системе без ETL. Но внутри часто всё равно **OLTP + отдельная аналитическая часть** за общим интерфейсом. Хранилище **не заменяет**; полезен, когда одному приложению нужно и то и другое (пример из книги — **антифрод**).
- **Product / real-time analytics** (Pinot, Druid, ClickHouse) — аналитические запросы, встроенные в продукт для пользователей: данные принимаются **в реальном времени**, оптимизация под **низкую задержку**. Классический OLAP — данные **пачками**, оптимизация под **пропускную способность**.

## 🧠 Как запомнить

- **OLTP** = «**кассир**»: обслуживает каждого покупателя быстро, по одному чеку.
- **OLAP** = «**бухгалтер в конце месяца**»: берёт все чеки разом и считает итоги.
