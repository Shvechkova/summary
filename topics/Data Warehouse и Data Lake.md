# Data Warehouse и Data Lake: хранилище данных и озеро данных

> **Теги**: #data #dwh #datalake #etl #olap #ddia

> *«Отличие от хранилища данных в том, что озеро данных просто содержит файлы, не навязывая никакого конкретного формата файлов, модели данных или схемы».*
> — Клеппман, Риккомини, «Высоконагруженные приложения», 2-е изд., гл. 1

## Краткое содержание
И **хранилище данных (data warehouse)**, и **озеро данных (data lake)** — это места, куда **копируют данные из операционных (OLTP) систем** для аналитики. Обе — **производные данные**, а не источник истины.

Главная разница:
- **Хранилище** — **реляционная БД с SQL**: данные уже **преобразованы и очищены**, лежат в удобной для анализа схеме. Для **бизнес-аналитиков**.
- **Озеро** — **просто файлы** любого формата, без навязанной схемы, в **«сыром»** виде. Для **data scientists** и всех, кто хочет преобразовать данные под себя.

## 🏛️ Хранилище данных (Data Warehouse)

**Откуда взялось** (по книге):
- Сначала одни и те же БД использовали и для транзакций, и для аналитики — SQL подходил для обоих.
- В **конце 1980-х — начале 1990-х** аналитику начали выносить в **отдельную БД** — её назвали **хранилищем данных**.

**Зачем** — аналитикам не стоит ходить напрямую в OLTP:
1. данные разбросаны по десяткам–сотням систем → трудно соединить в одном запросе (**data silos**);
2. схемы, удобные для OLTP, плохо подходят для аналитики;
3. тяжёлые аналитические запросы бьют по производительности OLTP;
4. OLTP может быть в закрытой сети по требованиям безопасности.

**Что это:**
- отдельная БД, которую аналитики могут нагружать **сколько душе угодно**, не мешая OLTP;
- содержит **read-only копию** данных **всех** OLTP-систем компании;
- обычно в компании **одно** хранилище — чтобы соединять данные разных систем в одном запросе;
- **реляционная модель + SQL**, часто через BI-софт (Tableau, Looker, Power BI);
- хранит данные **иначе, чем OLTP-базы** — под аналитические запросы (гл. 4).

**Как туда попадают данные — ETL:**
```
OLTP-базы ──Extract──► Transform ──Load──► Хранилище
           (дамп или      (схема для анализа,
            поток           очистка)
            изменений)
```
- **ELT** — сначала загрузить, потом трансформировать уже внутри хранилища.
- Источниками могут быть и **внешние SaaS** (CRM, email-маркетинг, процессинг карт) — через их API, с помощью коннекторов **Fivetran, Singer, Airbyte**.

**Примеры (табл. 1-2):** Teradata; облачные — **Snowflake** (хранит данные в S3), Google BigQuery, Azure Synapse Analytics.

## 🌊 Озеро данных (Data Lake)

**Почему понадобилось** (по книге): реляционное хранилище хорошо для бизнес-аналитиков, но неудобно **data scientists**:
- **feature engineering** — превращение строк и столбцов в векторы/матрицы признаков для обучения ML; требует кастомного кода, который трудно выразить на SQL;
- **NLP** по текстам (тональность отзывов, темы) и **компьютерное зрение** по фото.

Data scientists предпочитают **Pandas, scikit-learn, R, Spark**, а не реляционную БД.

**Что это:**
- **централизованный репозиторий** с копией **любых данных, которые могут пригодиться** для анализа, тоже через ETL;
- **просто файлы** — без навязанного формата, модели данных или схемы;
- внутри может быть что угодно: записи в **Avro / Parquet**, текст, картинки, видео, показания датчиков, разреженные матрицы, векторы признаков, геномы;
- **дешевле** реляционного хранилища — лежит на типовом хранилище, например **объектном** (S3 и т.п.).

**Принцип суши: «сырые данные лучше»**
- Данные лежат в том виде, как их произвели операционные системы, **без преобразования** в схему хранилища.
- Плюс: **каждый потребитель сам преобразует** сырые данные в удобную ему форму.

**Озеро как промежуточная остановка:**
- ETL обобщился до **конвейеров данных (data pipelines)**.
- Иногда озеро стоит **между** операционными системами и хранилищем:
```
OLTP-системы ──► Озеро (сырые файлы) ──► Хранилище (очищенные таблицы)
                       │
                       └──► data scientists, ML
```

## ⚖️ Сравнение

| | Хранилище данных (Data Warehouse) | Озеро данных (Data Lake) |
|---|---|---|
| Что внутри | Таблицы в реляционной схеме | Файлы любого формата |
| Схема | Навязана заранее (данные трансформированы под анализ) | Нет навязанной схемы, формата или модели |
| Вид данных | Преобразованные и очищенные | «Сырые», как из операционных систем |
| Типы данных | Структурированные записи | Что угодно: записи (Avro/Parquet), текст, фото, видео, датчики, векторы признаков, геномы |
| Как работать | SQL, BI-инструменты | Pandas, scikit-learn, R, Spark, свой код |
| Для кого | Бизнес-аналитики | Data scientists (и любые потребители, которым нужна своя форма данных) |
| Стоимость | Дороже | Обычно дешевле (объектное хранилище) |
| Кто преобразует данные | ETL заранее, один раз для всех | Каждый потребитель — под себя |

**Общее:**
- оба — **аналитические** системы и **производные данные** (не система записи);
- оба наполняются из операционных систем через **ETL / конвейеры данных**;
- оба содержат **копию** данных, а не оригинал.

## 🚀 За пределами озера (по книге)

- **DataOps** — внимание к эксплуатации аналитических систем и конвейеров (DataOps Manifesto); отчасти из-за **governance, приватности, GDPR/CCPA**.
- **Потоки событий** вместо файлов: аналитика реагирует **за секунды**, а не раз в сутки — например, чтобы ловить мошенничество.
- **Reverse ETL** — результаты аналитики возвращаются в операционные системы: ML-модель, обученная на данных из аналитики, выкатывается в прод и даёт рекомендации (TFX, Kubeflow, MLflow).

## 🧠 Как запомнить

- **Хранилище** = **библиотека**: книги отобраны, каталогизированы, стоят по полкам — бери и читай.
- **Озеро** = **склад**: свалено всё подряд как есть — дёшево, всё сохранено, но разбирать и приводить в порядок будешь сам.

> ⚠️ Метафоры и раздел «Как запомнить» — пояснения для понимания, не из текста книги. ASCII-схемы нарисованы по тексту главы (в книге есть только рис. 1-1 про ETL). Строки «Стоимость» и «Кто преобразует» в таблице сравнения — выводы из текста главы. Остальное — по главе 1.
