# Послесловие: подведём итог основных тем

## Что такое микросервисы

Тип сервис-ориентированной архитектуры с фокусом на **независимое развёртывание**. Изменения в одном микросервисе развёртываются без изменения других. Микросервисы развёртываются как процесс, связываются по сетевым протоколам, обычно работает несколько экземпляров.

**Скрытие информации:**

- За интерфейсом скрывается как можно больше (код, данные)
- Через интерфейсы — минимум для удовлетворения потребителей
- Чем меньше раскрытий — тем проще обратная совместимость

**Скрытие БД:**

- Внутренние БД не предоставляются внешним потребителям напрямую
- Избегать ситуаций, когда несколько микросервисов обращаются к одной БД

Микросервисы хорошо работают с **предметно-ориентированным проектированием (DDD)**.

## Переход к микросервисам

- Простой монолит с одним процессом — разумная отправная точка
- Понимать, чего хотите добиться (цель определяет способ разделения)
- Постепенная, эволюционная декомпозиция, а не переписывание «с размаху»
- Извлечь микросервис → развернуть → активно использовать → оценить продвижение к цели

## Стили взаимодействия

**Запрос — ответ:**

- Синхронный: ответ возвращается к отправившему запрос экземпляру
- Асинхронный: ответ может вернуться к другому экземпляру

**Событийное взаимодействие:**

- События = констатация факта
- Микросервис не сообщает другому, что делать, а делится событиями
- Асинхронное по природе
- Может требовать брокеров сообщений (управляемые снижают сложность)

Один микросервис может реализовать несколько протоколов (например, REST + события).

## Рабочий поток

Использовать **саги** для процессов с несколькими микросервисами, а не распределённые транзакции.

**Оркестрованные саги:**

- Централизованный оркестратор
- Простой подход
- Риск: оркестратор может делать слишком много, источник разногласий между командами

**Хореографические саги:**

- Нет оркестратора
- Ответственность распределена
- Более сложная реализация
- Менее подвержены повышению связанности
- Хорошо работают для нескольких команд

Оркестрованные саги — для одной команды, хореографические — для нескольких команд.

## Сборка

- У каждого микросервиса собственная сборка и конвейер CI
- Избегать ситуаций совместной сборки
- Автор не поклонник **монорепозиториев** (проблемы с правами собственности и сложностью сборок)
- Независимо от подхода — у каждого микросервиса свой процесс сборки CI

## Развёртывание

- Микросервис обычно развёртывается как процесс
- Возможные среды: физическая/виртуальная машина, контейнер, FaaS
- Максимальная изоляция микросервисов друг от друга
- **Контейнеры** — отличный выбор
- **Kubernetes** — для запуска на нескольких машинах; не рекомендуется для нескольких микросервисов; использовать управляемый кластер
- **FaaS** — интересная развивающаяся модель; развёртывание всего микросервиса как функции — хороший способ начать

**Разделить развёртывание и релиз:** канареечные релизы, параллельные запуски.

## Тестирование

- Набор автоматизированных функциональных тестов — хорошо
- **Сквозные тесты проблематичны** для микросервисов: дороже, больше сбоев не связанных с кодом
- Особенно сложны тесты, охватывающие несколько команд
- Альтернативы: контракты, управляемые потребителями, проверка совместимости схем, эксплуатационное тестирование

## Мониторинг и наблюдаемость

- **Мониторинг** — деятельность
- **Наблюдаемость** — степень понимания системы по внешним выходным данным
- Невозможно предсказать все причины сбоя
- Инструменты: **Lightstep, Honeycomb**
- В крупномасштабной системе проблема на одной машине — не повод для тревоги
- Использовать параллельные прогоны и синтетические транзакции

## Безопасность

- Микросервисы дают больше возможностей для глубокой защиты, но и больше точек атаки
- Автоматизация безопасности (патчи, сертификаты, секреты)
- **JWT-токены** для децентрализации авторизации (защита от **confused deputy problem**)
- **Нулевое доверие** — действовать так, будто система уже скомпрометирована

## Отказоустойчивость

Четыре ключевые концепции:

- **Надёжность** — поглощение ожидаемых возмущений
- **Восстановление** — после травмирующего события
- **Стабильная расширяемость** — справиться с неожиданной ситуацией
- **Непрерывная адаптивность** — постоянная адаптация

Микросервисы обеспечивают надёжность и восстановление, но не делают систему отказоустойчивой сами по себе. Модели стабильности: переборки, автоматические выключатели, тайм-ауты.

## Масштабирование

Четыре оси масштабирования:

- **Вертикальное** — мощнее машина
- **Горизонтальное дублирование** — несколько устройств для той же работы
- **Разделение данных** — по атрибутам (например, группы клиентов)
- **Функциональная декомпозиция** — по типу работы

Сначала простые способы (вертикальное, горизонтальное дублирование). Часто смешиваются типы.

## Пользовательские интерфейсы

- Не оставлять монолитный UI при разбиении бэкенда
- Нужны **потоковые команды** — владение сквозным фрагментом функций
- Использовать **микрофронтенды** (например, React)
- **Шаблон BFF (Бэкенд для фронтенда)** — для объединения и фильтрации на стороне сервера
- **GraphQL** — альтернатива BFF

## Организация

Переход от горизонтально выровненных команд к **потоковым командам**, сопровождаемым **командами поддержки** (сквозные направления: безопасность, удобство использования).

Для автономии — инструменты самообслуживания, **платформа** как **мощёная дорога** (необязательная).

## Архитектура

- Архитектура должна постоянно меняться
- Ответственность за техническое видение — совместный процесс
- Архитектор в башне из слоновой кости — препятствие
- При росте организации нужны люди, выделяющие время для изучения системы в целом
- Названия: главные инженеры, владельцы технических продуктов, архитекторы

## Взгляд в будущее

- FaaS второго/третьего поколения
- Kubernetes получит более широкое распространение, но будет скрываться за абстракциями
- Стандарт **Wasm** может изменить представление о развёртываниях
- **Unikernel** может получить вторую жизнь
- Ожидается обратная реакция против микросервисов после критической массы негативных примеров

## Заключительные слова

- Принимать каждое решение небольшим по объёму
- Принять концепцию **эволюционной архитектуры**
- Не масштабные преобразования, а серия небольших изменений
- Микросервисы — путешествие, а не пункт назначения
- Дисциплина постоянного изменения и развития — самый важный урок
