
## 📌 **Главная идея главы**

> **Data Mesh — это DDD для аналитики**.  
> Традиционные подходы (Data Warehouse, Data Lake) создают монолитные, хрупкие, централизованные системы аналитики.  
> **Data Mesh** переносит принципы **ограниченных контекстов**, **владения данными** и **инкапсуляции** на аналитические данные — и позволяет масштабировать аналитику вместе с бизнесом.

---

## 🔍 **1. OLTP vs OLAP: две модели, две цели**

| Характеристика | **OLTP (транзакционные)** | **OLAP (аналитические)** |
|----------------|--------------------------|--------------------------|
| **Цель** | Обработка операций в реальном времени | Анализ, отчёты, ML, BI |
| **Потребители** | Пользователи, сервисы | Аналитики, DS, BI-инструменты |
| **Модель** | Сущности и отношения (ER-диаграммы) | **Факты + Измерения** |
| **Данные** | Точные, текущие, детализированные | Агрегированные, исторические, часто сэмплированные |
| **Операции** | CRUD, транзакции | Чтение, агрегация, срезы |

### 🔸 Факт (Fact)
- Описывает **бизнес-событие** (продажа, регистрация, обращение в поддержку).
- Аналог **Domain Event**, но без строгого требования к имени.
- **Неизменяем**: новые состояния — новыми записями.
- Пример: `Fact_Sales`, `Fact_CustomerOnboardings`.

### 🔸 Измерение (Dimension)
- Описывает **контекст факта**: *кто, где, когда, как*.
- Атрибуты: `Customer`, `Product`, `Region`, `Time`.
- Связано с фактами через **внешний ключ**.

### 📊 Схемы аналитических моделей:
- **«Звезда»**: факты в центре, измерения напрямую связаны.
- **«Снежинка»**: измерения нормализованы → меньше дублирования, но сложнее запросы.

## 🏛️ **2. Традиционные архитектуры аналитики**

### 🏢 **Data Warehouse (DWH)**
- **ETL**: извлекает данные → **трансформирует в аналитическую модель** → загружает.
- Часто **читает напрямую из OLTP-БД**, игнорируя API → **сильная связанность**.
- Проблемы:
  - Монолитная модель «на всё предприятие» → не масштабируется.
  - Любое изменение в OLTP ломает ETL.
  - Аналитики **не знают бизнес** так глубоко, как команда продукта.

> 💡 Витрины данных (Data Marts) — частичное решение, но не устраняют корневые проблемы.

### 🌊 **Data Lake**
- Хранит **«сырые» данные** в исходном виде.
- Трансформация — **по запросу**, аналитиками.
- Плюсы:
  - Гибкость: можно строить **много моделей**.
  - Поддержка ML, streaming и т.д.
- Минусы:
  - **Болото данных**: хаос, дубли, отсутствие схемы.
  - Аналитики тратят **80% времени на очистку**, а не на анализ.
  - Множество версий ETL → **технический долг**.

> ❗ **Общая проблема**: централизация, отрыв от бизнеса, хрупкость.

## 🕸️ **3. Data Mesh: новый парадигмальный сдвиг**

Data Mesh — **декомпозиция аналитики по предметным областям**, с **владением данными у команд продукта**.

### 🔑 **4 принципа Data Mesh**

#### 1. **Данные по предметным областям (Domain-Oriented Data Ownership)**
- Каждый **ограниченный контекст** владеет **и OLTP, и OLAP**.
- Команда продукта отвечает за:
  - Транзакционную модель
  - **Аналитическую модель** (преобразование, публикация)
- Границы OLAP-моделей = границы Bounded Context.

> 🎯 Устраняет «аналитический центр» → знания остаются у экспертов.

#### 2. **Данные как продукт (Data as a Product)**
- Аналитические данные — **публичный продукт**, как API.
- Требования к «продукту данных»:
  - **Обнаруживаемость** (каталог данных)
  - **Документированная схема**
  - **SLA** (доступность, свежесть, качество)
  - **Версионирование** и обратная совместимость
  - **Поддержка разных форматов** (SQL, Parquet, API и т.д.)

> 💡 Команды продукта **включают data-инженеров** → кросс-функциональность.

#### 3. **Автономия через платформу (Self-Serve Data Infrastructure)**
- Чтобы не каждый изобретал «колесо», создаётся **единая платформа аналитики**:
  - Шаблоны для публикации данных
  - Инструменты для мониторинга, качества, доступа
  - Поддержка polyglot persistence (разные хранилища)
- Платформа → **команда инфраструктуры данных**.

#### 4. **Федеративное управление (Federated Governance)**
- Централизованные **правила и стандарты**:
  - Формат метаданных
  - Политики безопасности
  - Качество данных
- Но **исполнение децентрализовано** → команды соблюдают правила самостоятельно.
- Управление — **совет владельцев данных + платформенная команда**.

## 🔗 **4. Как DDD поддерживает Data Mesh**

| DDD-концепция | Применение в Data Mesh |
|--------------|------------------------|
| **Ограниченный контекст** | Граница владения данными (OLTP + OLAP) |
| **Единый язык (Ubiquitous Language)** | Аналитическая модель использует термины бизнеса |
| **Open-Host Service** | OLAP-модель = **Published Language** для аналитики |
| **CQRS** | Идеален: **Write Model** = OLTP, **Read Model** = OLAP |
| **Паттерны интеграции** | ACL для «плохих» аналитических моделей, Customer-Supplier для согласования |

> 💡 **CQRS позволяет**:
> - Поддерживать **несколько версий** OLAP-моделей
> - Обновлять аналитику **независимо** от транзакционной системы

## ✅ **Выводы**

1. **OLAP ≠ OLTP** — разные цели, разные модели, разные потребности.
2. **Data Warehouse и Data Lake** — устаревшие, централизованные подходы, не масштабируемые в сложных организациях.
3. **Data Mesh** — **DDD для аналитики**:
   - Декомпозиция по доменам
   - Владение данными у команд продукта
   - Данные как продукт с SLA
4. **DDD-паттерны напрямую применимы**:
   - Bounded Context → границы данных
   - CQRS → разделение OLTP/OLAP
   - Published Language → аналитический API

> 🔄 **Data Mesh не заменяет DWH или Lake — он меняет подход к владению и архитектуре данных**.
