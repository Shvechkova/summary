### 🔑 Основная цель

Реализация **сложной бизнес-логики** (в отличие от простой CRUD-логики из главы 5) требует **модели предметной области (Domain Model)** — шаблона, в котором данные и поведение объединены в объекты, выражающие **бизнес-правила**, **инварианты** и **состояния**.

Этот подход применяется в **основных поддоменах (core subdomains)**, где логика критически важна для получения конкурентного преимущества.
> Паттер- ном является «модель предметной области», а агрегаты и объекты-значения явля- ются его строительными блоками.
---

**Модель предметной области (доменная модель):**

Паттерн предназначен для **сложной бизнес-логики**, где важны **состояния, правила и инварианты**, а не просто CRUD-операции.

- Реализует **поведение и данные в одном объекте**, в отличие от пассивных моделей вроде Active Record.
- Строится из **тактических блоков DDD**: агрегаты, объекты-значения, доменные события и сервисы.
- **Фокус на бизнес-логике**, а не на инфраструктуре — модель состоит из чистых объектов без зависимостей от БД или фреймворков.
- Код **отражает единый язык (Ubiquitous Language)** и ментальные модели экспертов предметной области.

Используется в **основных поддоменах**, где логика критична и сложна (например, управление жизненным циклом заявок с SLA, эскалацией, автоматическими действиями).

---
### 🧱 Строительные блоки модели предметной области

#### 1. **Объект-значение (Value Object)**

- Идентифицируется **по значениям своих полей**, а не по ID.
- **Неизменяем** — любое «изменение» создаёт **новый экземпляр**.
- Инкапсулирует **валидацию и поведение** (например, `PhoneNumber.Parse()`, `Money.Add()`).
- Устраняет **одержимость примитивами** (Primitive Obsession) — вместо `string email` → `EmailAddress`.
- Делает код **выразительным, безопасным и соответствующим единому языку**.
- Примеры: `Color`, `Money`, `Email`, `Height`, `CountryCode`.

> Используйте объекты-значения **везде, где возможно** — особенно для свойств сущностей.

> ✅ Используется для описания **свойств сущностей**.
> С позиции бизнес-области полезным практическим правилом является использова- ние объектов-значений для элементов предметной области, описывающих свойства других объектов.
---

#### 2. **Сущность (Entity)**

- Имеет **уникальный идентификатор** (ID), который сохраняется на протяжении всей жизни.
- Может **изменяться** (в отличие от объектов-значений).
- Пример: `Person` с `PersonId`.

> ⚠️ **Важно**: в DDD сущности **почти никогда не существуют сами по себе**.  
Они входят в состав **агрегата (Aggregate)** — корневой сущности, которая:

- является **границей согласованности**,
- **защищает инварианты**,
- **является точкой входа** для всех изменений.
---

#### 3. **Агрегат (Aggregate)**
**Агрегат** — это **группа связанных объектов** (сущностей и объектов-значений), которые рассматриваются как **единое целое** для обеспечения **согласованности данных** и **транзакционной целостности**.

> Агрегат — это **граница**, внутри которой все бизнес-правила и инварианты должны оставаться **всегда согласованными**.

Агрегат **всегда имеет корень** — одну главную сущность, через которую **весь внешний мир взаимодействует с агрегатом**.
## 🔸 Зачем нужны агрегаты?

### Проблема без агрегатов:

- Бизнес-логика распределена по коду.
- Нарушаются инварианты (например: «эскалированная заявка не может быть закрыта агентом»).
- Возможны частичные обновления («сохранили сообщение, но не обновили статус заявки»).
- Конкурирующие изменения портят данные.

### Решение с агрегатами:

- Вся логика — **внутри агрегата**.
- Все изменения — **через корень**.
- Все данные агрегата — **в одной транзакции**.
- Согласованность — **гарантирована**.

---

## 🔷 Структура агрегата

Любой агрегат состоит из:

| Компонент                            | Описание                                                                                              |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------- |
| **Корень агрегата** (Aggregate Root) | Основная сущность. Единственная точка входа. Имеет глобальный идентификатор.                          |
| **Внутренние сущности**              | Существуют только внутри агрегата. Имеют локальный идентификатор (уникальный только внутри агрегата). |
| **Объекты-значения**                 | Неизменяемые данные (электронная почта, приоритет, сообщение и т. д.).                                |
| **Инварианты**                       | Правила, которые **должны соблюдаться всегда** после любых изменений.                                 |

---

## 🧪 Пример из книги: заявка в техподдержку (`Ticket`)

### Требования (из текста):

- Клиент может повысить приоритет заявки.
- Эскалированная заявка **не может быть закрыта агентом**.
- Если агент не читает сообщения в течение 50 % времени, отведенного на SLA, заявка **автоматически переназначается**.
- Сообщения — часть заявки.

→ Это **единый контекст согласованности** → всё это **один агрегат**.

##### Ключевые принципы:

- **Изменение только с помощью команд** (открытые корневые методы). 
-  Команды могут быть простыми методами (`AddMessage`) или объектами(бъект-параметр) (`Execute(AddMessage cmd)`).
- **Все изменения — в рамках одной транзакции**.
- **Один агрегат = одна транзакция** → нельзя обновлять несколько агрегатов в рамках одной транзакции.
-  Вся **бизнес-логика и инварианты** инкапсулированы внутри агрегата — это гарантирует согласованность.
- **Слой приложения** лишь загружает агрегат, вызывает команду и сохраняет результат — он прост и не содержит логики.
- Внутри агрегата может быть **иерархия сущностей и объектов-значений**, если они требуют **строгой согласованности**.
- На другие агрегаты ссылаются **только по ID**, чтобы не нарушать границы транзакций.
-  Для защиты от конфликтов при параллельных изменениях используется **оптимистическая блокировка** (поле `_version` + проверка при сохранении).
-  Агрегат может публиковать **события предметной области** (в прошедшем времени), чтобы другие части системы реагировали на изменения.
- Весь код агрегата должен отражать **единый язык (Ubiquitous Language)**.

Отдельно - **Иерархия сущностей и границы агрегата:**

- **Сущности существуют только внутри агрегата** — они не используются самостоятельно.
- **Агрегат** — это корневая сущность, объединяющая **иерархию сущностей и объектов-значений**, которые **должны быть строго согласованы** в рамках **одной транзакции**.
- Всё, что участвует в **бизнес-правилах, требующих атомарного обновления**, должно входить в один агрегат (например, заявка и её сообщения).
- На объекты **вне агрегата** (другие агрегаты) ссылаются **только по ID**, чтобы не нарушать транзакционные границы.
- **Агрегат должен быть минимальным**: включать только то, что **требует строгой согласованности**; всё остальное — через eventual consistency.

##### События предметной области (Domain Events)

- Публикуются агрегатором при важных изменениях (например, `TicketEscalated`).
- Названия — в **прошедшем времени**.
- Используются для **реакции других компонентов** (асинхронно, через шину событий).

---

#### 4. **Доменный сервис (Domain Service)**

- **Без состояния**.
- Содержит логику, **не принадлежащую ни одному агрегату**, но требующую данных из нескольких источников.
- Пример: расчёт SLA с учётом приоритета заявки, графика работы агента и политик отдела.

> ❗ Не путайте с микросервисами или API-сервисами — это просто **объект с бизнес-методами**.

---

### 🎯 Как модель управляет сложностью?

- **Инварианты инкапсулируются** внутри агрегатов и объектов-значений.
- Это **снижает степень свободы системы** → поведение становится **предсказуемым и контролируемым**.
- Логика **не дублируется** на уровне приложения — она сосредоточена в модели.

> 💡 Сложность никуда не исчезает — она **организуется и локализуется**.

---

### 📌 Когда применять?

- Только в **основных поддоменах** с **высокой сложностью бизнес-логики**.
- Не для CRUD, ETL, интеграций — там достаточно **транзакционного сценария** или **активной записи**.

---

### ✅ Вывод

Модель предметной области — это **богатая, поведенчески ориентированная модель**, в которой:

- код **говорит на языке бизнеса** (универсальный язык),
- данные и логика **неразделимы**,
- согласованность **гарантируется архитектурой**, а не надеждой на дисциплину разработчиков.

Это **сердце DDD** — инструмент для решения **настоящих бизнес-задач**, а не просто для хранения данных.

---

### ✅ Активная запись (Active Record) и **Модель предметной области (доменная модель):** различия:

Разница между **Активной записью (Active Record)** и **Моделью предметной области (Domain Model)** — это разница между **простой объектной обёрткой над таблицей** и **богатой поведенческой моделью бизнес-логики**.

---

### 🔹 **Активная запись (Active Record)**

- **Цель**: упростить CRUD-операции с данными.
- **Структура**: объект = строка в БД + методы `Save()`, `Delete()`, `Find()`.
- **Логика**: минимальная — валидация, простые правила.
- **Данные и поведение**: данные публичны или легко изменяемы извне (`user.Name = "..."`).
- **Зависимость от БД**: тесная — объект знает, как сохраняться.
- **Пример**:
    
var user = new User { Name = "Alice" };
user.Save(); // внутри — INSERT в БД
    

> ✅ Подходит для **вспомогательных поддоменов**, где логика простая (например, управление пользователями, справочниками).

---

### 🔹 **Модель предметной области (Domain Model)**

- **Цель**: точно отразить **сложную бизнес-логику**, инварианты, состояния, правила.
- **Структура**: состоит из **агрегатов**, **объектов-значений**, **доменных сервисов**, **событий**.
- **Логика**: сосредоточена **внутри объектов**, инкапсулирована.
- **Данные и поведение**: данные **недоступны для прямого изменения** — только через команды (`ticket.Escalate(reason)`).
- **Зависимость от БД**: **отсутствует** — модель чистая, инфраструктура отделена.
- **Пример**:
    
    var ticket = repository.Load(id);
ticket.RequestEscalation(reason); // внутри — проверка правил, генерация события
repository.Save(ticket);
    

> ✅ Подходит для **основных поддоменов (core)**, где бизнес-логика сложна и критична (например, расчёт SLA, эскалация заявок, финансовые операции).

| Критерий | **Активная запись** | **Модель предметной области** |
|---|---|---|
| **Сложность логики** | Простая (CRUD, валидация) | Сложная (инварианты, состояния, правила) |
| **Инкапсуляция** | Слабая (поля часто публичны) | Сильная (изменение только через методы) |
| **Зависимость от БД** | Есть (объект знает, как сохраняться) | Нет (чистая модель, сохранение — через репозиторий) |
| **Повторное использование логики** | Низкое (логика размазана по слою приложения) | Высокое (вся логика — в модели) |
| **Тип поддомена** | Supporting / Generic | Core |
| **Тестируемость** | Сложнее (из-за зависимости от БД) | Проще (чистая модель без побочных эффектов) |


### 💡 Главное отличие:

> **Active Record — это данные с методами.**  
> **Domain Model — это поведение с данными.**

Active Record — инструмент для **хранения**, Domain Model — инструмент для **мышления** на языке бизнеса.
